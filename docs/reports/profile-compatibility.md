# Сопоставление

| Возможность | Исходный сервер | Форк | Проверка/граница |
|---|---|---|---|
| Многофайловая раскладка | 12 фиксированных section-файлов | docsDir, полная карта sections в `.arc42.yaml`, отдельные дочерние документы | Custom paths и нестандартное имя корня проверяются тестами |
| Building Blocks | Текстовые шаблоны уровней | Рекурсивные building-blocks/name/README.md, kind, parent | У внутренних уровней trigger 1..5 и evidence; истинность условия проверяется содержательно |
| Runtime | Общий раздел | scenarios/*.md и явные blocks | Ссылки на реальные блоки; Level 1 overview не подменяет участника |
| ADR | Предлагается append в section 9 | Отдельные MADR minimal 4.0, уникальные номера ADR-xxxx | Проверяются ключевые разделы и непустое содержание; решение человека не принимается автоматически |
| Frontmatter | Не обязателен | title/type/status/updated для каждого Markdown в docsDir | Типы, даты, роли, superseded_by и циклы |
| Инициализация | Все разделы, images, общий документ; force перезаписывает | Minimal: индекс, requirement, Level 1; full — 12 черновиков по явному выбору | Существующие материалы не перезаписываются; конфликты раскладки и параллельный init отклоняются |
| Точечная правка | Полный replace/append | Read → SHA-256 → единственный exact-match edit → atomic rename | Общий lock/CAS; внешние редакторы не участвуют в кооперативном lock |
| Ссылки | Не проверяются | Markdown inline/reference links, images, anchors, HTML href/src и явные metadata refs | Внешние URL и code symbols не запрашиваются; локальные пути code проверяются |
| Согласованность | Word-count «полнота» | Типы/роли, parent, runtime blocks, требования, статусы источников, цепочки замены | Содержательная истинность относительно кода требует review |
| Legacy | Специальных операций нет | Read-only inventory, exact duplicates, metadata health, scoped migration plan со снимком хешей | Только выбранные source/target/reason и действующее requirement; переносов нет |
| Requirements и Diátaxis | Не разделены процедурой | Отдельные типы и расположение; requirement содержит описание.md | Открытый текст требований не копируется в архитектуру автоматически |
| C4 | Можно вставлять диаграммы | Диаграммы рядом с разделом, проверка путей | Не выполняется автоматический C4-анализ |
| MCP | 6 tools, 11 языков, Markdown/AsciiDoc | 10 tools, прежние 6 сохранены | Прежний stdio workflow и новый workflow проверяются собранным сервером |

# Выбор применения стандартов

[Официальный arc42 Building Block View](https://docs.arc42.org/section-5/) допускает иерархические blackbox/whitebox и выбор релевантной глубины. Локальные триггеры углубления уточняют этот выбор; они не объявлены общим правилом arc42. Машина проверяет существование evidence и допустимый trigger, а warning decomposition-review требует проверить смысл основания.

[Runtime View](https://docs.arc42.org/section-6/) описывает архитектурно значимые взаимодействия блоков. Явные blocks связывают статическое и динамическое представления, но не доказывают правильность последовательности действий.

[Arc42 section 9](https://docs.arc42.org/section-9/) допускает ADR и отдельные решения с рациональным основанием. [MADR minimal 4.0](https://github.com/adr/madr/blob/4.0.0/template/adr-template-minimal.md) используется для структуры отдельного документа. Поля date и decision_status — явный выбор адаптера; decision-makers необязателен. Status документа не смешивается с состоянием решения. Английские заголовки MADR являются ключами проверки; текст может быть русским.

Официальный section 1 предусматривает краткий обзор движущих требований. Локальный профиль хранит исходные требования отдельно: в архитектуре следует давать только архитектурный контекст и ссылки, без второго полного текста требования. Генератор upstream сохранён как справочный шаблон; агент адаптирует его к локальному профилю.

Полный пустой scaffold не создаётся по умолчанию: это противоречило бы требованию создавать только нужные материалы. Явный full создаёт заполненные инструкциями черновики; наличие этих файлов не означает готовность архитектуры. Это разрешённая опция инструмента, а не рекомендация заранее заполнять все разделы продукта.

# LOOP и независимые проверки

Использован цикл из задания: Ponytail → Validator → Critic → исправления → повторная проверка → holistic audit. Поиск отдельного текста LOOP прекращён по указанию пользователя. Никакие дополнительные обязательные правила неизвестной версии протокола не заявляются выполненными.

Ponytail: расширен существующий реестр; используются Zod/YAML и stdlib. Для полноценного разбора Markdown добавлен marked. Не создавались отдельная БД документов, плагины миграции или второй реестр содержания.

Validator независимо проверил snapshot 4335561 и воспроизвёл ошибки custom mapping, каталога вместо обязательного файла, обхода сканирования, системного overview вместо runtime-блока, неоднозначной инициализации, служебных пересечений и symlink-корня. Исправления покрыты тестами. Содержательная истинность триггера вынесена в явное предупреждение, а не имитируется автоматикой.

Critic независимо проверил snapshot 0cd1339 и воспроизвёл гонку двух режимов init, отсутствующий targetFolder и конфликт роли notes/level1.md. Добавлены общая блокировка init, создание нового корня после preflight и проверка роли раскладки. Детерминированное воспроизведение гонки повторено: успешен один init, workspace остаётся однозначным.

Старый Skill отдельно проверен как RED baseline: он описывал общий ADR append и не давал безопасного product workflow. Обновлённый Skill прошёл независимый GREEN forward-test из 26 вызовов по реальным схемам. Сохранены неизвестные поля и байты после stale edit; созданы nested block/runtime/MADR; inventory и план не изменили ни один из 12 исходных файлов fixture.

# Проверки сборки и поставки

Baseline после исправления native OXC tsconfig discovery: 1308 исходных тестов. Текущий полный suite: 1341 тест в 26 файлах, включая собранный stdio MCP. Сборка TypeScript успешна. Финальный прогон через npm lifecycle: statements 94,58%, branches 84,99%, functions 99,11%, lines 97,18%; пороги upstream пройдены.

Повторная установка из lockfile выполнена через `npm ci --offline --ignore-scripts --no-audit` из локального npm cache; обычный сетевой npm ci при завершающем прогоне завис на получении пакетов и был остановлен. Сборка и тесты после чистой offline-установки прошли. Дополнительно проверены 33 конфигурации: 22 сочетания 11 языков с Markdown/AsciiDoc upstream и 11 языков full product-профиля.

`npm pack` создал устанавливаемый архив с 312 файлами, включая dist, обе лицензии, NOTICE, Skill с references, установку, контракт и этот отчёт. Архив установлен с production-зависимостями в отдельном временном каталоге. Сервер запущен через stdio из установленного пакета: проверены tools/list (10 tools), product init/read/CAS/status/validate/inventory/migration-plan и upstream DE/AsciiDoc. Проверка Skill через quick_validate и локальные ссылки новых документов также прошли.

Обновлены lockfile и безопасные версии зависимостей в пределах разрешённых диапазонов. Неиспользуемые chokidar и gray-matter удалены после проверки всех импортов. Production audit: 0 уязвимостей. Полный audit оставляет 3 moderate в dev-цепочке Vitest; стандартный audit fix их не устраняет. Это отражается как остаточное ограничение инструментов тестирования; production-пакет их не устанавливает.

Holistic audit сопоставил итоговый код и пакет с требованием и таблицей профиля. Проверены границы двух режимов, сохранность исходников, обязательность Level 1, раздельные источники requirements/architecture/ADR, безопасность правки, отсутствие исполняемой автоматической миграции, установка Skill и путь получения upstream-обновлений. Проверка inventory дополнительно обнаружила и исправила смешивание разных не-UTF8 файлов при текстовом хешировании: теперь хешируются исходные байты, кодировка не меняется.

Осознанные ограничения: `update-section replace` сохранён для совместимости, в product требует expectedHash; точечные изменения выполняются через arc42-document. Внешний редактор может попасть в окно между последней проверкой хеша и atomic rename; гарантируется координация MCP-процессов по общему lock. Истинность evidence/архитектуры и смысловые конфликты требуют владельца. Эти ограничения не скрыты за valid=true.

npm lifecycle pretest:coverage собирает dist перед coverage, поэтому протокольный suite в исходном CI не пропускается. Файл workflow сохранён равным upstream: GitHub-токен не имеет workflow scope. Пакет форка имеет собственное имя и private: true; установка выполняется из Git/локального архива, npm publish блокируется самим package.json. Действие публикации npm не выполнялось.

# Лицензии и upstream

Код распространяется под [Apache-2.0](https://www.apache.org/licenses/LICENSE-2.0). Сохранены LICENSE, attribution и NOTICE; изменённые исходники помечены как изменения форка. Шаблоны arc42 сохраняют [CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/), attribution создателей и указание изменений в создаваемом индексе. Это разные лицензируемые части проекта. Vendor submodule не изменён.

Исходная Git-история сохранена, upstream доступен отдельным remote. Изменения сосредоточены в новых product-модулях, реестре и коротких ветках существующих handlers. После обновления upstream требуется повторная сборка и весь suite: гарантия бесконфликтного merge не заявляется.

Ни один legacy-документ пользователя не перенесён автоматически. Материалы вне нового checkout не редактировались. Существующая документация самого upstream также не мигрировалась массово.
